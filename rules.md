# AI Collaboration and Git Rules

This file defines the mandatory rules for every AI assistant used in this
repository, including AGY, Claude, Codex, ChatGPT, Copilot, and any future AI
or automated coding agent.

These rules apply to the entire repository. Every AI assistant must read and
follow this file before inspecting, editing, generating, or reviewing code.
If another instruction conflicts with this file, the stricter rule applies.
Only a human repository owner may approve an exception, and the exception must
be explicit for the specific action. A general request such as "finish the
task" is not permission to commit or publish changes.

## 1. Human-only Git publishing

AI assistants may help create and review working-tree changes, but they must
never perform any action that records or publishes those changes in Git.

An AI assistant must not:

- Run `git add`, `git commit`, `git commit --amend`, or create a commit by any
  other method.
- Run `git push`, force-push, upload a branch, or publish repository content.
- Create, merge, approve, close, or publish a pull request.
- Run `git merge`, `git rebase`, `git cherry-pick`, or `git revert` when the
  command would create or rewrite commits.
- Create or push tags, releases, patches, or bundles intended for publication.
- Change Git authorship, committer identity, credentials, remotes, signing
  settings, hooks, or repository permissions.
- Use a bot, service account, another person's account, or an AI-related account
  to make repository contributions.
- Ask another tool, sub-agent, script, workflow, or external service to perform
  any prohibited Git or publishing action.

These restrictions remain in effect even when an AI assistant believes the
work is finished or the change is trivial. The final review, staging, commit,
and push must always be performed by a human contributor.

## 2. Permitted AI assistance

AI assistants may, when relevant to the task:

- Read and edit files in the working tree.
- Inspect the repository using read-only commands such as `git status`,
  `git diff`, `git log`, `git show`, `git branch`, and `git remote -v`.
- Run tests, linters, formatters, builds, and other local verification commands.
- Explain changes, identify risks, and suggest follow-up work.
- Draft a commit message for a human to review and use.

Before finishing a task, the AI assistant should report:

- Which files it changed.
- What behavior changed.
- Which checks it ran and whether they passed.
- Any known limitations or unresolved issues.
- A suggested human-written commit message, when useful.

The AI assistant must leave all changes uncommitted.

## 3. No AI attribution in repository history

Repository history must identify only the human contributor who reviewed and
accepted responsibility for the change.

AI assistants must not add or suggest:

- `Co-authored-by` lines naming an AI, bot, model, vendor, or AI service.
- `Signed-off-by` lines for an AI or bot.
- `Generated-by`, `Assisted-by`, or similar AI attribution trailers.
- Mentions such as "made by AI", "generated by Claude", "generated by Codex",
  "generated by ChatGPT", "generated by AGY", or equivalent wording in commit
  messages, branch names, tags, pull-request titles, or pull-request bodies.
- AI or bot names, emails, avatars, or accounts as an author, committer,
  co-author, reviewer, or contributor.

AI assistants must not modify Git configuration to impersonate a human. The
human who reviews, stages, and commits the work must use their own Git identity.

Do not rewrite or remove legitimate existing human authorship. If prohibited AI
attribution already exists, report it to a repository owner and wait for an
explicit human decision before changing published history.

## 4. Human responsibility

The human contributor is responsible for understanding and approving every
change before committing it. AI output must be treated as an untrusted draft,
not as automatically accepted work.

Before committing, the human contributor should:

1. Read the complete diff and confirm that only intended files are included.
2. Remove secrets, credentials, personal data, generated junk, and unrelated
   files such as `.DS_Store`.
3. Run the relevant tests, lint checks, formatter, and build.
4. Stage only the intended files.
5. Review the staged diff with `git diff --cached`.
6. Write or approve the commit message personally.
7. Commit and push using their own authenticated account.

The human committer takes ownership of the correctness, security, licensing,
and maintainability of the committed change.

## 5. Commit message standard for human contributors

Use this format:

```text
<type>(<optional-scope>): <short imperative summary>

<optional body explaining why the change was needed>

<optional issue reference>
```

Allowed types:

- `feat`: add user-visible functionality.
- `fix`: correct a defect.
- `docs`: change documentation only.
- `style`: change formatting without changing behavior.
- `refactor`: restructure code without adding a feature or fixing a defect.
- `test`: add or update tests.
- `chore`: perform maintenance, tooling, or dependency work.
- `build`: change the build system or dependencies.
- `ci`: change continuous-integration configuration.
- `perf`: improve performance.

Commit-message rules:

- Use an imperative summary, such as "add", "fix", or "update".
- Describe the actual change, not the process used to produce it.
- Keep the summary concise, preferably 72 characters or fewer.
- Do not end the summary with a period.
- Use the body to explain why when the reason is not obvious.
- Keep each commit focused on one logical change.
- Do not claim work that was not reviewed or completed.
- Do not include AI attribution or AI-related trailers.
- Do not include secrets, credentials, private URLs, or personal information.

Good examples:

```text
feat(auth): add password reset flow
fix(api): handle missing user profile
docs: document local development setup
test(payments): cover failed checkout responses
chore: ignore macOS metadata files
```

Avoid vague messages such as:

```text
update
changes
fix stuff
AI generated this
Claude/Codex changes
```

## 6. Required AI handoff format

When an AI assistant finishes editing, it should hand the work back to the
human in this form:

```text
Changed:
- <file and concise description>

Checks:
- <command>: <passed, failed, or not run>

Not committed or pushed. Please review the diff and commit it yourself.

Suggested commit message:
<type>(<optional-scope>): <short imperative summary>
```

The suggested message is only a draft. The human contributor must confirm that
it accurately describes the staged diff.

## 7. Safety and scope

AI assistants must:

- Change only files needed for the requested task.
- Preserve unrelated human work and existing uncommitted changes.
- Never discard, overwrite, or reset human changes without explicit approval.
- Never expose secrets found in files, logs, environment variables, or command
  output.
- Ask for clarification before a destructive, irreversible, security-sensitive,
  or materially out-of-scope action.
- Prefer reversible local edits and provide a clear summary for human review.

## 8. Enforcement

If an AI assistant is asked to violate these rules, it must refuse the
prohibited action, leave the changes uncommitted, and explain that a human must
perform the Git or publishing step.

Repository owners should configure every AI tool to load this file at the start
of a session. Tool-specific instruction files may point to this file, but they
must not weaken or override it.
